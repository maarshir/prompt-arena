# prompt-arena

Прогоняет несколько вариантов промпта по одним и тем же задачам и показывает, где ответы разошлись.

Одной фразой для резюме: инструмент для сравнения промптов на наборе задач с чёткими проверками ответов, без оценок «на глаз».

## Зачем

Когда правишь промпт, легко улучшить три случая и незаметно сломать два других. Средняя оценка тут мало что даёт: она может вырасти, пока половина случаев ломается. Поэтому в отчёте важны сами расхождения: какая задача у какого варианта прошла, а у какого нет.

Пригодится тому, у кого модель делает одну и ту же работу много раз: разбирает фразы в поля, отвечает по шаблону, классифицирует. Первый набор задач как раз такой: разбор свободной фразы про день («выпил 300 мл и был в зале») в строку с полями. Похожую работу делает мой [ассистент](https://github.com/maarshir/assistant).

## Что готово

- Формат набора задач и загрузчик с проверкой файла.
- Варианты промпта в отдельном YAML (`prompts/`), тоже с проверкой файла.
- Проверки ответов: `exact`, `contains_all`, `contains_none`.
- Асинхронный вызов модели (Anthropic API): повторы только там, где повтор может помочь, пауза с разбросом, не больше заданного числа одновременных запросов.
- Прогон `run.py`: каждый вариант по каждой задаче, проверка ответов, итоги по вариантам (сколько прошло, сколько не прошло, сколько сбоев, токены, время) и список расхождений. Все ответы сохраняются в JSON.
- 50 тестов. Сеть в них подменена, ключ не нужен. На Гитхабе тесты прогоняются автоматически перед слиянием ветки в main.

Настоящего прогона с результатами в репозитории пока нет: для него нужен ключ к модели. Кэша ответов и отчёта в Markdown и HTML тоже пока нет, см. «Что дальше».

## Как запустить

Нужен Python 3.10 или новее.

```bash
git clone https://github.com/maarshir/prompt-arena.git
cd prompt-arena
python -m venv .venv
source .venv/bin/activate      # на Windows: .venv\Scripts\activate
pip install -r requirements.txt
pytest
```

### Прогон

```bash
cp .env.example .env           # и впишите в .env свой ANTHROPIC_API_KEY
python run.py --prompts prompts/parse_day.yaml --cases cases/parse_day.yaml
```

Посмотреть, что уйдёт в модель, можно без ключа и без затрат:

```bash
python run.py --prompts prompts/parse_day.yaml --cases cases/parse_day.yaml --dry-run
```

Параметры: `--model` (по умолчанию `ARENA_MODEL` из `.env` или `claude-sonnet-4-6`), `--limit` (сколько запросов одновременно, по умолчанию 5), `--out` (куда сохранить JSON, по умолчанию папка `results/`).

Так выглядит итог в консоли. **Это не настоящий прогон:** ответы и число токенов придуманы для примера, модель подменена так же, как в тестах. Настоящий пример появится здесь после первого прогона с ключом.

```
вариант       прошло   нет  сбой   токены вх/вых     сек
short          5/7       2     0          420/42     5.6
rules          7/7       0     0         1120/42     5.6

Расхождения (задача: кто прошёл):
  gym_no: short нет, rules да
  sleep_range: short нет, rules да
```

Главное здесь нижний блок. Он показывает, на каких именно задачах один вариант справился, а другой нет. Сбои сети и отказы API выводятся отдельно и в расхождения не попадают: если ответа нет, промпт в этом не виноват.

### Проверки на ответах, написанных руками

Пример работы проверок без модели:

```bash
python -m examples.check_by_hand
```

```
two_facts       да   water=0.5; gym=да; sleep=0
gym_no          нет  Конечно! gym=да
nothing_useful  да   Пусто.
```

Во второй строке ответ «зал был», хотя в фразе «зал сегодня пропустил», да ещё с «Конечно!» в начале. Проверка это ловит.

## Как описать варианты промпта

Файл в `prompts/`, список вариантов. `prompt` уходит в модель как системный промпт, `input` задачи как сообщение пользователя.

```yaml
- id: short
  note: минимум слов, только формат
  prompt: |
    Извлеки из фразы пользователя данные о дне и ответь одной строкой
    в формате: water=литры; gym=да|нет; sleep=часы
    ...
```

## Как описать задачи

Набор задач лежит в YAML, по файлу на тему. Пример из `cases/parse_day.yaml`:

```yaml
- id: gym_no
  input: зал сегодня пропустил
  expect:
    contains_all: ["gym=нет"]
  note: отрицание, частая ошибка
```

- `id`: уникальное имя, по нему потом сравниваются варианты;
- `input`: что получит модель;
- `expect`: какие проверки должен пройти ответ, все одновременно. Можно не указывать, тогда задача ничего не проверяет;
- `note`: зачем эта задача нужна. Необязательно, но через месяц сам не вспомнишь, что тут ловили.

Загрузчик падает с понятной ошибкой, если нет `id` или `input`, если `id` повторяется или если проверка названа неизвестным словом.

## Проверки

- `exact`: точное совпадение, для ответов в одно-два слова;
- `contains_all`: все нужные факты на месте, формулировка любая;
- `contains_none`: нет лишнего вроде «Конечно! Вот ответ».

Все возвращают да или нет. Баллов нет специально: под них пришлось бы выдумывать порог.

Перед сравнением нормализация срезает регистр, лишние пробелы и точку в конце. Точку модели ставят почти всегда, даже когда просишь одно слово.

## Технологии и почему они

- **Python** без фреймворков: проект маленький, по модулю на каждую часть: загрузка задач и вариантов, проверки, клиент, прогон.
- **YAML** для задач: их пишут руками, а в YAML списки и русский текст читаются проще, чем в JSON.
- **pytest** для тестов.
- **httpx** для запросов к API: асинхронный клиент из коробки, а в тестах `MockTransport` подменяет сеть без сторонних библиотек.
- **asyncio** с семафором: запросы идут параллельно, но не больше `--limit` одновременно, чтобы не упереться в ограничения API.
- **pytest-asyncio** для тестов асинхронного кода.
- **GitHub Actions**: ветка сливается в main, только если тесты прошли.

## Что было непросто

- **Чем мерить ответ.** Напрашивается оценка от 0 до 1, как у многих систем оценки. Но тогда нужен порог «сколько считать хорошо», и он всё равно выдуманный. Проще и честнее да или нет: если не можешь записать ожидание как проверку, значит, сам не до конца понимаешь, чего ждёшь от модели.
- **Мелочи, которые ломают точное сравнение.** «Да.», «да» и «Да » для человека одно и то же, а для `==` нет. Отсюда нормализация. Резать надо осторожно: только края, регистр, пробелы и точку с восклицательным знаком в конце, иначе можно случайно «починить» действительно неверный ответ.
- **Опечатка в названии проверки.** Если написать `contain_all` вместо `contains_all`, проверка молча не сработает, и задача будет проходить всегда. Такую ошибку можно не замечать неделями, поэтому загрузчик сверяет названия со списком известных и падает сразу.
- **Сбой сети не должен выглядеть как плохой промпт.** Если один вариант получил 529 от перегруженного API, а другой нет, простое «прошло или нет» покажет ложное расхождение. Поэтому у результата отдельное поле `error`: такие задачи считаются сбоем, выводятся отдельным списком и не попадают в расхождения.
- **Что повторять.** Повторять стоит только 429, 5xx и обрывы сети. 400 или 401 от повтора не исправятся, а потратят время. Паузу удваиваем, но с разбросом: иначе десяток параллельных запросов, получив отказ одновременно, одновременно же пойдут повторять и снова упрутся в ограничение.
- **Как тестировать без ключа.** Прогон принимает функцию запроса параметром, поэтому логику можно проверить на подменённых ответах. Отдельный тест идёт через настоящий клиент и подменяет только сеть: первый запрос получает 429, и видно, что повтор срабатывает внутри целого прогона.

## Что дальше

- Первый настоящий прогон и его результаты в README.
- Кэш ответов, чтобы повторный прогон не тратил деньги.
- Отчёт в Markdown и HTML: таблица задачи на варианты, отдельно список расхождений. В отчёте же стоимость каждого варианта через [token-counter](https://github.com/maarshir/token-counter).
- Известные слабые места проверок, которые стоит закрыть:
  - `contains_all` ищет подстроку, поэтому `water=0.3` найдётся и в `water=0.35`. Для полей вида `ключ=значение` нужна проверка с границей значения;
  - загрузчик не проверяет типы: `exact: 5` без кавычек сейчас приводит к ошибке при проверке, пишите `exact: "5"`.
